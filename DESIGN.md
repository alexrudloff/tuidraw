# Native control design

Reference: tuiparts button, badge, switch, and semantic theme recipes. The terminal is a developer demo surface where compact controls and visible state matter more than decoration.

Each generated interface carries a model-chosen theme: background, surface, foreground, muted, border, primary, focus, danger, success and warning. All colors are #RRGGBB; light and dark palettes are supported. Choose hues and contrast to suit the requested subject rather than imposing a fixed amber/cyan scheme. Shared primitives consume these roles, and filled controls choose readable label contrast. Preserve the palette during refinement unless a recolor is requested. Legacy specs without a theme use the charcoal/amber fallback. ANSI art, scene legends, QR codes and intrinsic card/equalizer colors retain their authored or functional colors. Preserve color-independent focus through borders and bold text. Buttons distinguish neutral, primary, and destructive intent; badges pair color with labels; switches explicitly say On/Off.

Live controls compose Input/Text/Button primitives inside a generic Grid. The model proposes grouping and row-major placements; code applies targeted edits, renders cells and executes shared operations. Jev shared style selection and operand grounding are enabled by default by user preference; `--engine llm` skips them; layout does not require a second model call. The legacy imported Keypad keeps its fixed calculator/numeric layout, but is excluded from live generation. The host chat overlays the bottom of the preview without changing its viewport.

TUI Draw is used by a developer iterating in their everyday terminal, alongside source and shell output. Keep the host on the terminal's native surface with the embedded theme accent for keyboard actions and focus. Startup uses the user-provided OpenCode screenshots as a polish reference: restrained ink background, distinct dialog surfaces, strong selected rows, deliberate whitespace and grouped actions. A centered bordered project picker offers genuine Open/New/Add existing/Delete buttons, keyboard navigation and mouse clicks. Delete acts on the selected project and opens a Cancel/Delete confirmation, initially focused on Cancel, then moves the full folder to recoverable sibling trash. The launcher is a generated spec rendered by our own primitive widgets. Panel.surface is a reusable way to request the contrasting theme surface; omission preserves existing backgrounds. The canvas has only a one-line footer naming the project and showing save state plus Chat/Projects shortcuts. Ctrl+G toggles a bottom chat overlay with scrollable conversation, progress/errors, and a prompt. Esc hides chat; drafts survive. Opening chat never changes the generated layout's viewport. Ctrl+P returns to projects; Ctrl+N/O remain shortcuts. Project folder forms use the same centered editor at startup and while editing.


Presentation is independent of domain content: panels offer border, padding, gap and title alignment; shared width bounds and alignment avoid unnecessary full-width controls. Rows can collapse below a declared width and grids reduce columns by minimum cell width. Height measurement, rendering and focus geometry share these rules. Searchable selectors and multi-select lists filter locally, preserve committed state while typing and show explicit chosen markers. Tables use column widths, alignment and semantic colors rather than separate domain widgets. Defaults preserve existing projects. These additions take behavioral inspiration from Clime and use Ratatui's native widgets, not Go terminal input loops.

Use explicit fixed, content-sized, or filling widths for new layouts. A rail gets a cell width, a workspace fills the remainder, and a compact action fits its label. Default application titles to ordinary compact text and let the working area receive extra height. The generator sees native measured boxes and can declare gap, size, and edge checks; repairs must satisfy the original checks. Geometry is verified locally, without an extra model call on a successful first proposal.

Shared chrome lives in `theme.design`: border (plain/rounded/double/heavy), density (compact/comfortable), and emphasis (quiet/bold). Bordered controls, selection lists and visual surfaces use the same border family; panel titles and metric values share emphasis. Containers inherit gap, panels inherit padding, and tables inherit padding/column gap. Null or omitted properties inherit; explicit widget values win. Legacy themes omit design and retain their former defaults. The design persists and exports with the ordinary theme, without a new runtime dependency.

Native layout reports include standing audits for empty areas and clipped controls, plus warnings for artwork width and low text contrast. Scrolling is allowed; wrapping prose is not treated as clipped artwork. These conservative checks complement model-declared geometry requirements; they are not a visual-quality score. No screenshot critic or extra model repair loop is involved.

Numeric color rules belong to primitives, not domain recipes. Metric, Gauge, Sparkline and BarChart accept a base color and ordered inclusive thresholds. Resolve colors against current values on each render, preserving live bindings; each bar resolves independently and a sparkline uses its latest sample. Keep numeric labels alongside color. A request to color a particular value preserves the overall shared theme.

The project picker uses one compact title and outer frame. Global New/Add existing actions are above the list; selected-project Open/Delete actions are below it. One primary action anchors the group, destructive entry actions stay quiet, and confirmations default to Cancel. Keyboard hints track focus; feedback never replaces them. Deletion offers real Undo with occupied-path and writer-lock protection. Generic Button.variant="plain" uses one bracketed row, preserving focus, disabled state and actions. Select/MultiSelect.bordered=false omits their frame/title when the surrounding region already supplies context; defaults preserve old specs. Generation, refinement, repair and Jev receive the same task hierarchy, grouping, honest affordance and recovery guidance without another model call.

Every new button needs a discoverable keyboard accelerator. Button.hotkey is part of the generic control contract; rendering and width audits include its key label. Code assigns unique missing keys (prefer Alt mnemonics, then function keys), preserves existing bindings on replacement, and rejects collisions. The content and Jev instructions require this without inventing shortcut text. Host chat/navigation and native popups isolate dispatch; disabled or hidden actions cannot trigger. Exported shortcuts route through the same custom-action hook and rollback as Enter. The launcher shows direct accelerators on all buttons, using a distinct Alt+Y for destructive confirmation.
